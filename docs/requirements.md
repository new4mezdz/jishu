# 密集签子与棒材端面计数工具需求文档

文档版本：1.0

更新日期：2026-10-10

项目阶段：首期最小可用版本（MVP）需求整理

当前交付范围：需求文档；应用功能尚待实现。

## 项目目标

开发一个基于照片的计数工具，识别照片中每个可见签子或棒材端面的中心位置，按有效位置点的数量统计，并允许用户检查、补点和删除误检。

计数结果必须能够逐点核查。不得通过大模型直接估算总数，不得以总面积除以单根面积代替逐目标识别，也不得按照未经验证的数量调整输出。

只统计照片中具有视觉证据、能够识别的可见端面。对于完全被遮住、照片中没有视觉证据的目标，不猜测补数。

首期目标场景是大量密集排列的白色圆形或近圆形棒材端面，可能存在阴影、倾斜、紧贴和局部遮挡。后续使用真实竹签照片验证和扩展；白色棒材上的效果不能直接证明支持所有竹签场景。

当前尚未收到原始样图，也没有经过人工核对的位置标注或数量真值。此前提到的约 3,400～3,500 根只是未验证的估计，禁止将其用作训练标签、验收答案、算法调参目标或程序中的固定数量。

## 首期范围与边界

首期建议实现本地运行的 Web 应用，优先支持电脑浏览器，并兼顾 iPhone 浏览器上传照片。默认使用 CPU 运行，图片在本地处理，不依赖第三方付费识别接口。

建议路线是先完成 Web 闭环和传统算法基线，再根据真实数据接入专用模型。这是实施建议，不是必须遵守的技术限制；若已有仓库采用合适技术栈，优先复用。

首期不实现以下功能：

- 账户系统、支付和云端多租户服务。
- 实时视频计数和原生 iOS App。
- 完全遮挡目标的数量推断。
- 复杂训练平台或未经实际验证的准确率、速度承诺。

传统算法的职责是提供可运行基准和辅助标注，不要求首期自动结果一根不差。业务可接受误差应在实际评估后确定。

## 用户流程

1. 上传照片，显示方向正确的预览。
2. 确认或手动调整计数区域。
3. 执行自动检测，获得每个候选端面的位置及自动检测数量。
4. 在原图上逐点显示标记，用户通过缩放、拖动和隐藏标记检查局部细节。
5. 点击空白处补点，点击已有标记删除误检，必要时撤销操作。
6. 保存自动检测结果、人工修正结果和核对状态。
7. 用户完整检查后主动确认“已完成人工核对”；未完整核对时也允许保存和导出，但必须保留未核对状态。
8. 导出带标记图片和 JSON／CSV 标注数据。

## 首期功能要求

### 图片输入与方向处理

- 至少支持 JPG／JPEG 和 PNG，验证实际文件内容及能否解码。
- 保存上传的原始文件；识别使用完整分辨率图像，不得因前端预览缩放而丢失识别细节。
- 正确处理图片方向信息，包括 EXIF 方向。前端显示、检测和导出使用同一方向校正结果。
- 记录上传原图尺寸和方向校正后的尺寸，保留两者的关联。
- 不支持的格式应明确提示。若首期不支持 HEIC／HEIF，iPhone 用户上传此类文件时应收到清晰提示，不能表现为无响应或通用识别失败。
- 对无法解码、资源限制或图像处理失败给出明确原因。资源限制必须配置化，不得悄悄缩小原图后仍宣称按原图完成检测。

### 识别区域

- 支持手动框选矩形计数区域，默认可使用整张图。
- 用目标中心是否落在区域内决定是否计入，排除纸箱、背景等无关内容。
- 区域在原图坐标系中保存；前端缩放和拖动不会改变其实际位置。
- 区域边缘附近的检测应保留必要图像上下文，不能仅因端面跨越区域边缘而漏掉中心位于区域内的目标。
- 区域变更后创建新的未核对结果版本；再次检测不覆盖原结果和原人工修改记录。

### 自动检测与结果反馈

- 输出每个目标的位置、唯一 ID 和检测方法，并显示自动检测数量。
- 能够运行单图数千个密集目标的完整检测流程，不设置与算法能力无关的固定最大目标输出数量。
- 自动检测数量始终等于该次检测结果中区域内有效自动点的数量。
- 检测期间显示处理状态，失败时显示明确提示。
- 没有可用候选、图像无法处理或算法不适用时，明确提示需要检查区域、图片或人工处理，不返回伪装成精确答案的估计数。
- 即使返回 0 个候选，也不能自动视为经过人工确认的零目标图片。
- 不得编造概率置信度。如果算法只有响应强度等指标，应按其真实含义命名；没有可靠分数时允许为空。

### 可视化核查

- 在方向校正后的原图上显示所有有效点。
- 支持缩放、拖动以及显示／隐藏标记，放大后可逐点核查漏检和重复检测。
- 自动识别点和人工新增点使用可区分的标记，并配有简明图例。
- 画面变化时标记与端面始终对齐，点击命中范围不得因缩放导致明显难用。
- 对数千个标记保持可操作性；实际响应时间通过测试记录，不预先承诺固定速度。

### 人工纠错与撤销

- 点击区域内空白位置新增人工点；点击已有标记删除该点。
- 区域外点击不新增计数点，并给出明确反馈。
- 显示的修正后数量始终等于当前区域内有效点数，每次增删或撤销立即更新。
- 支持连续撤销本次编辑中的新增和删除操作；撤销应恢复点的 ID、坐标及来源。
- 删除自动点只改变修正结果，不删除该次自动检测基线。
- 对同一位置附近的交互应优先命中已有标记，减少误新增重复点。

### 保存与导出

- 保存原始图片、区域、自动检测结果、人工修改记录、最终有效点和人工核对状态。
- 导出 JSON 和 CSV 标注数据，以及与当前结果一致的带标记图片。
- 导出图片使用方向校正后的原图坐标，保持可核查的分辨率；任何缩放或裁剪导出都必须明确记录对应变换。
- JSON 保存完整数据关系；CSV 至少输出点 ID、坐标、来源、有效状态，并提供关联的图片 ID、结果版本和核对状态。
- 导出结果明确区分“自动检测数量”“人工修正后数量”“是否完成人工核对”。
- 未经完整人工核对的结果不标记为“真实数量”。

## 数据状态、版本与修改历史

### 数据单位

以原始照片为数据单位，每张照片具有稳定的图片 ID。每次检测产生独立结果版本，保留该版本的区域、检测方法、参数和时间。

每张图片至少保存：

- 原始上传文件及方向校正图像或可复现该图像的方向信息。
- 原图与方向校正后图像的宽高、图片 ID，以及已有时可用的拍摄批次 ID。
- 各结果版本的识别区域、检测方法、实现或模型版本、必要参数。
- 不可变的自动检测点集合和自动检测数量。
- 人工新增、人工删除及撤销记录，最终有效点集合和修正后数量。
- 人工核对状态，以及完成核对的时间。

照片、运行数据和测试产物默认保存到项目外的独立数据目录，通过配置指定位置，避免进入代码提交。

### 核对状态

建议使用以下状态：

| 状态 | 含义 |
| --- | --- |
| 未核对 | 已生成或导入结果，用户尚未完整检查 |
| 核对中 | 用户正在检查或已做人工修改，但尚未确认完成 |
| 已核对 | 用户明确确认已完整检查当前区域内的所有有效点及漏检 |

不得因为自动检测完成、用户修改了少数点、数量接近估计值或点击保存，就自动标记为已核对。

用户确认核对完成时，保存与该点集合及区域绑定的结果快照。继续新增、删除或撤销时，从该快照建立新的修订，状态为“核对中”；区域调整或重新检测产生的版本状态为“未核对”。历史快照及其核对记录保留，不能将已确认的状态沿用到发生变化的结果。

### 重新识别与修改记录

- 原始自动检测结果保持不变，便于分析算法漏检和误检。
- 人工删除保留被删除点的 ID 和来源，不能只留下最终数量。
- 重新识别创建新版本，不能静默覆盖旧自动结果或人工修正。
- 新检测结果不自动叠加旧人工点。若未来支持迁移修正，需要明确点的关联方式并重新核对。
- 最终有效点可从基线和编辑记录重建；保存及导出时检查数量与有效点集合一致。

## 坐标、区域与前端映射约定

所有最终坐标统一到方向校正后的完整原图坐标系。设图像宽高为 `W`、`H`，左上角为坐标原点，`x` 向右增加，`y` 向下增加；目标中心可使用浮点数，且必须位于图像有效范围内。

矩形区域保存为 `x_min`、`y_min`、`x_max`、`y_max`，采用半开区间：

```text
x_min <= x < x_max
y_min <= y < y_max
```

区域限制在图像范围内，整图区域为 `[0, W) × [0, H)`。自动点、人工点、数量统计和数据导出使用同一个中心判定函数。

前端屏幕坐标由原图坐标加上缩放和拖动变换得到；用户点击新增点时必须执行逆变换。若图片周围存在留白，需计入图片实际绘制位置，不能把容器坐标直接当作图片坐标。

裁剪和切片内部坐标返回时，先恢复任何局部缩放，再加上裁剪／切片相对于完整原图的偏移。算法和接口层负责返回原图坐标，避免前端重复加偏移。

需要验证方向校正、不同缩放倍率、拖动、区域边界、切片偏移与导出之间的坐标一致性。

## 检测方案与可替换接口

### 传统算法基线

首期建议使用 Python 和 OpenCV 实现可实际运行的圆检测或斑点检测基线，流程如下：

```text
读取完整原图并校正方向
→ 确定计数区域和必要上下文
→ 预处理
→ 检测端面候选位置
→ 排除明显误检
→ 合并重复检测
→ 按中心过滤计数区域
→ 返回原图坐标和自动检测数量
```

应考虑端面尺寸差异、明暗变化和倾斜。尺寸范围、预处理方式、候选筛选、切片尺寸、重叠范围及去重参数应配置化，首期不要求复杂参数面板。

算法调参不得以得到约 3,400～3,500 个点为目标。当前没有人工真值，任何检测数量都只是待核查结果。

### 统一检测接口

前后端使用统一检测结果结构，后续可将传统算法替换为目标检测或中心点检测模型而不重写整个应用。

每个自动目标至少包含：

| 字段 | 要求 |
| --- | --- |
| `id` | 在结果版本内唯一，保存后稳定 |
| `x`、`y` | 方向校正后完整原图中的中心坐标 |
| `method` | 检测方法名称 |
| `bbox`／`size` | 可选，确有相应检测依据时填写 |
| `score`、`score_type` | 可选，说明分数实际含义；无可靠分数可为空 |

结果级信息包括图片 ID、结果版本、图像尺寸、区域、检测方法及版本、参数、处理状态、耗时和自动点集合。接口不把自动检测结果直接等同于人工核对结果。

### 专用模型阶段

使用对应场景的真实数据训练或微调模型。不能假设通用预训练模型直接就能准确数签。

模型接入沿用同一坐标、结果版本和人工纠错流程。GPU 训练或推理能力在后续阶段按需增加，首期不构建复杂训练平台。

## 高密度图片、切片与去重

避免将整张高分辨率照片缩到端面细节无法分辨。识别模块应支持或预留以下流程：

```text
高分辨率原图
→ 带重叠和必要上下文的切片
→ 各切片检测
→ 坐标映射回完整原图
→ 跨切片去重
→ 按区域中心规则过滤并汇总
```

实现时必须满足：

- 根据目标尺寸和算法上下文需求设置切片重叠，保证接缝附近具有完整检测机会。
- 图片最外侧和切片最后一行、最后一列也被覆盖，不因整除关系留下空白区域。
- 同一目标在多个切片出现时合理合并，保留稳定的最终点。
- 去重阈值结合目标尺寸和实际位置证据确定，不能仅用过大的固定距离把紧贴的两个真实端面合并。
- 检查算法或模型的候选数量限制、每切片最大输出量等配置，避免密集场景被静默截断。
- 切片和去重结束后检查坐标范围与唯一性；重叠区域不会重复计数。

首期闭环完成后再优化密集场景。优化效果必须通过逐点核查确认，不能仅以最终总数变多、变少或接近估计值判断。

## 标注积累与数据划分

人工纠错数据用于积累后续模型训练资料，但只有用户明确完成核对的版本才能进入人工核对参考集。未核对结果可作为待标注材料，不能直接当作真值。

中心点标注和检测框标注是不同的数据。如果选用需要检测框的模型，必须补充可靠的框或目标尺寸信息，不能把仅有中心点的数据直接当成完整检测框标签；算法估算的尺寸也不能默认视为人工确认的框。

训练、调参与测试按原始照片或拍摄批次划分。来自同一原始照片的切片不得分别进入训练集和测试集；同一批次具有高度相似性的照片应避免造成评估数据泄漏。

比较传统算法与专用模型时，使用同一批未参与训练和调参、且经过完整人工核对的照片，保持相同区域、计数范围和匹配规则。

## 评估方法

### 逐点匹配

使用人工核对的端面中心作为参考，检测点和参考点进行一对一位置匹配。一个检测点最多匹配一个参考点，一个参考点最多匹配一个检测点。

评估前约定位置容差，可结合端面尺寸确定，并记录在评估配置中。容差不得临时放宽以获得更好结果。匹配规则应在可用候选中优先保证有效匹配数量，再减少位置距离；实现方法和参数保持一致。

- 匹配成功的点：正确检测。
- 未匹配的参考点：漏检。
- 未匹配的检测点：误检，包括对同一目标的重复检测。

没有人工位置标注时，只能评估已确认的总数误差，不能据此宣称已经测得漏检数或误检数。

### 主要指标

至少记录每张图片的：

- 计数绝对误差：自动检测数量与人工核对参考数量之差的绝对值。
- 漏检数量和误检数量。
- 计数完全正确的图片比例，并同时报告其中是否仍有相互抵消的漏检与误检。
- 检测耗时、图片尺寸、区域、硬件及检测方法和参数。

检测耗时定义为后端读取和处理图片至坐标汇总完成的时间，不含上传时间及用户纠错时间。比较时采用相同测量口径。

不能只比较最终总数，因为漏检与误检可能相互抵消。暂不承诺 99.9% 等未经验证的准确率或固定处理速度。

## 首期验收

### 功能闭环验收

使用支持格式的真实照片完成“上传 → 区域选择 → 检测 → 逐点显示 → 人工修正 → 保存 → 导出”。至少确认：

- 上传原图分辨率被保留，带方向信息的图片显示和检测方向一致。
- 自动数量、修正后数量分别与对应有效点集合一致。
- 新增、删除、连续撤销行为正确，自动基线没有被人工删除操作覆盖。
- 自动点和人工点可区分；显示／隐藏标记、缩放和拖动可用于局部核查。
- 人工核对只能主动确认，修改后状态失效；保存、重新打开和导出保持相同状态及数量。
- 调整区域或重新识别产生新版本，历史检测及人工修改仍可追溯。
- JSON／CSV 和带标记图片与保存结果一致，能关联回相应图片和结果版本。
- 不支持格式、解码失败、检测失败及没有可用候选时得到清晰提示。

### 坐标与密集场景验收

使用外部独立验证材料检查：

- 原图、预览、区域和导出的同一点位置一致。
- 不同缩放、拖动、方向校正和切片偏移下点击坐标映射正确。
- 中心恰好落在区域边界时遵循统一半开区间规则。
- 同一目标跨切片时不会重复计数；接缝附近不会因缺少上下文明显漏检。
- 紧邻的两个真实端面不会被不合理的去重阈值合并。
- 在提供的数千目标真实场景照片上能够完成检测和纠错流程，记录实际数量与耗时；数量不能按未经验证估计验收。

可使用已知点位置的独立验证图片检查几何、统计和交互逻辑，但这类材料不能替代真实照片的算法效果评估。

### 效果验收边界

首期算法效果通过人工核对照片的逐点匹配结果记录，不以“所有照片自动一根不差”为上线前提。具体业务误差阈值在获得真实数据后另行确认。

尚未收到样图或尚无人工核对数据时，必须明确说明真实场景识别效果尚未验证，不能完成该部分效果验收。

## 推荐技术栈与交付要求

默认建议 Python + FastAPI + OpenCV 后端、Vue 3 + Canvas 前端。该建议允许根据已有代码和实际运行环境调整。

应用开发阶段交付：

- 可运行的前后端代码和依赖配置。
- 本地启动说明，以及电脑和 iPhone 浏览器访问、上传的必要说明。
- 接口说明，包括输入格式、状态、坐标和错误反馈。
- 检测参数说明及本地图片、结果数据的存储配置。
- 原始检测与人工修正数据格式、导出格式和版本约定。
- 坐标转换、区域边界、切片去重、数量一致性及人工增删／撤销等关键逻辑的可执行测试或验证脚本，在项目外的独立目录交付；项目内提供运行说明。

遵守项目约定：测试代码、测试输入、生成的结果、报告和缓存不得放入当前代码项目，以免影响后续 Git 提交和推送。需要验证时使用项目外的独立目录，项目中只记录运行方法及所需依赖；运行验证时也应避免在项目内生成测试缓存。

## 实施优先级

1. 图片上传、原图保留、方向处理、显示与区域选择。
2. 传统算法检测、统一坐标接口与逐点标记。
3. 缩放拖动、人工补点、删点和撤销。
4. 结果版本、人工核对状态、保存与 JSON／CSV／标记图片导出。
5. 密集场景优化、重叠切片、跨切片去重和实际性能记录。
6. 整理人工核对数据，训练专用模型，并在相同独立测试集上与传统算法比较。

开发时先检查现有项目结构，优先实现最小可用闭环，不以架构文档代替可运行应用，不提前搭建复杂训练平台。

## 待获取材料与待确认事项

- 用户提到的原始照片：当前尚未提供。需要原始文件作为开发测试输入，不能把截图或缩小的预览默认当作高分辨率原图。
- 人工核对参考：需要逐点确认可见端面的位置和区域，得到与该区域一致的参考数量。未经核对的约 3,400～3,500 根估计始终不作为真值。
- 后续真实竹签照片：用于验证场景扩展，不能仅凭白色棒材结果推断支持程度。
- 图片格式、尺寸和拍摄批次信息：根据真实素材确认必要限制与数据分组。
- 业务可接受误差及位置匹配容差：在获得真实照片、目标尺寸和评估记录后确定，不预先捏造指标。

这些材料不会阻止先开发上传、坐标映射、纠错和导出闭环，但真实场景算法调参与效果验收必须以收到素材和人工核对数据为前提。
